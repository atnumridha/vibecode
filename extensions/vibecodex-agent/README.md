# Vibe Codex Agent

Vibe Codex Agent is the installable VS Code extension identity for the native VibeCode agent.

In the VibeCode build, this extension delegates to the native workbench agent surface for visual planning, approvals, diffs, checkpoints, provider selection, and Codex backend integration.

In an external VS Code install, the extension provides the same command and sidebar entrypoint while guiding users to configure a local Codex CLI command. The VSIX activates from both `vibecodex.extension.*` commands and native `vibecodex.*` aliases so bundled VibeCode wiring and external callers can wake the same extension surface before the sidebar opens.
The installable sidebar and localhost preview panels use a strict webview Content Security Policy with `default-src 'none'`, nonce-scoped inline styles/scripts, local `webview.cspSource` assets only, no `unsafe-inline`, and preview `frame-src` constrained to the safe target origin plus the extension webview source. The sidebar also narrows `localResourceRoots` to extension media assets and attaches `taskId`, `revision`, and `planHash` to every rendered-plan approve/refine/reject/edit action, so stale webview clicks are rejected before execution authorization changes.
Use `Ctrl+K` / `Cmd+K` from an editor to open the inline prompt against the active file or selected range, then route that prompt into the same visual planning and approval flow. External installs build an inline prompt session with selected code, nearby context before/after the range, required plan steps, acceptance criteria, and a sidebar Inline Prompt card before any mutation is allowed. The Inline Prompt Readiness panel mirrors that backend status into target, selection/context sizes, required plan steps, acceptance criteria, and exact-plan authorization match beside the card. Reconnected backends can call `agent/getInlinePromptStatus`, `agent/inlinePromptStatus`, `inlinePrompt/status`, or `inline_prompt_status` to inspect the active inline prompt target, captured plan requirements, optional redacted prompt/context, and exact-plan authorization match without gathering fresh editor text, approving plans, or mutating files.
It can also hand a prompt to the configured Codex CLI in a workspace terminal for Ask, Plan, Manual, Act, Agent, Debug, Review, and Custom mode workflows.
Each mode is backed by an enforced Mode Policy. Plan, Ask, Manual, and Review are read-only in the extension bridge and block backend terminal, file, tool, browser, MCP, and diff-acceptance requests. Act, Agent, Debug, and Custom can request those actions only after the exact visual plan revision has been approved. The Mode Policy panel shows the active allowed/blocked action set, and the Mode Readiness panel mirrors the current mode, all standard modes, exact-plan authorization match, and next safe route. Backend mode status requests through `agent/getModeStatus`, `agent/modeStatus`, `mode/status`, or the `mode_status` / `mode_policy_status` / `current_mode` tools return that read-only mode readiness without switching modes, approving plans, running tools, accepting diffs, or mutating files. The same policy is sent to Codex app-server and CLI fallback prompts.
Workspace custom modes are discovered from Cline/Roo-style `.roomodes` files plus `.cline/modes.*` and `.vibecodex/modes.*`. The Custom Modes panel shows each mode slug, source, role definition, usage guidance, group permissions, and whether the mode is read-only or execution-capable after visual plan approval; the same catalog is sent to Codex app-server, CLI fallback prompts, session history, and Markdown exports.
Terminal execution is also constrained by a Cline-compatible Command Permissions panel. The extension merges VS Code allow/deny settings with `CLINE_COMMAND_PERMISSIONS`, blocks dangerous shell patterns first, applies deny rules before allow rules, and still requires exact visual plan authorization before any backend terminal run can start. Backend `agent/validateCommand`, `agent/commandValidation`, `command/validate`, `terminal/validate`, or `command_validate` requests are read-only terminal command validation requests that classify command intent, command permissions, Mode Policy readiness, cwd sandbox state, verification linkage, risk, and repair hints without creating approval cards, starting terminals, interrupting/retrying commands, approving plans, or unlocking execution. The Command Validation Readiness panel mirrors the last backend command candidate into command kind/risk, permission decision, mode/plan gate, cwd sandbox safety, verification linkage, blockers, warnings, repair hints, and read-only command guardrails beside Command Permissions. Cline-compatible `execute_command`, `run_command`, `run_commands`, `terminal`, `bash`, and `shell` tool calls are surfaced as terminal approval cards; `commands: string[]` payloads are normalized into one visible approval candidate joined with `&&`. Accepting the card starts the command in the visible Vibe Codex pseudoterminal, returns a `runId` to the backend, streams throttled redacted `agent/terminalOutput` deltas while the process runs, and reports completion through the normal `agent/terminalResult` evidence stream. ## Installation

VibeCode builds load this extension identity as `vibecodex.agent` and set it as the `product.json` default chat agent, so the built-in product uses Vibe Codex while inherited Copilot chat entrypoints stay suppressed.

External VS Code installs use the same VSIX:

1. Run `npm --prefix extensions/vibecodex-agent run package-vsix` from the repository root.
2. Verify the generated `extensions/vibecodex-agent/vibecodex.agent-<version>.vsix.sha256` sidecar before distributing the VSIX.
3. Install the generated VSIX path printed by the packager, for example `code --install-extension extensions/vibecodex-agent/vibecodex.agent-0.1.6.vsix`.
4. Configure `vibeCodex.extension.codexCommand` and, when needed, `vibeCodex.extension.transport`, `vibeCodex.extension.pipePath`, `vibeCodex.extension.websocketUrl`, or `vibeCodex.extension.messageFraming`. Existing Codex CLI login and `~/.codex/config.toml` provider defaults are picked up automatically.

The extension declares limited untrusted-workspace support: read-only planning and context UI can load, while mutation, terminal execution, and parallel worktree preparation stay behind approval and trust gates.
